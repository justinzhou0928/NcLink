# NC-Link 掉线隔离测试报告

**问题**：同时接入 4 台机台，其中 1 台突然掉线后，其余 3 台也无法访问。

**结论摘要**

| 对象 | 结论 | 证据强度 |
|---|---|---|
| 我们自己实现的 C# 客户端（方案 B） | **掉线隔离正确**；曾在测试中发现一处**响应关联缺陷，已修复并验证** | 实测，见下 |
| 官方 apiServer | **无法判定** —— 它在当前环境里从一开始就连不上设备 | 实测，见下 |

> **重要更正**：本报告初版只写了「其余设备未受影响」，漏掉了测试中一个自相矛盾的现象——
> 某台**已确认杀死**的设备在几秒后仍返回 `OK`。追查后确认是**我们自己代码**里的响应关联缺陷
> （`ProbeAsync` 用 `deviceId` 兜底匹配，而 `deviceId` 也出现在响应主题里，
> 导致该设备的迟到响应被后续请求误领）。已修复并验证，详见
> [响应关联修复与验证.md](./响应关联修复与验证.md)。
>
> 教训：**测试工具的输出必须逐项自洽检查**。当时若只看「存活设备 0 失败」就收工，
> 这个缺陷会带着上线。另外原测试用「缓存查询」测出的 0–1ms 延迟是缓存命中，
> 不能反映真实网络往返，后来改为每次 Probe 真实往返。

---

## 一、测试方法

用 4 个**独立的模拟机床进程**（每台一个进程，便于精确终止单台），4 台同时接入，
运行中杀掉其中 1 台，然后持续探测其余设备。

测试脚本（可复跑）：

- `tests/run-isolation-test.ps1` —— 总入口（`-Target csharp` / `-Target apiserver`）
- `tools/NcLink.IsolationTest/` —— 探测工具，统计每台设备的成功/失败次数
- `tests/test-apiserver-isolation.ps1` —— apiServer 的 HTTP 侧探测

探测内容：每台设备每秒发一次 `Query/Request`（读 `/MACHINE/STATUS`），
超时 2.5 秒，记录成功/失败与延迟。

## 二、我们自己的 C# 客户端：没有该 bug

`pwsh -File tests/run-isolation-test.ps1 -Target csharp -Duration 26`

```
=== 结果统计 ===
设备                    成功    失败   最后错误                 最后耗时
STRESS_TEST_00000      10      5   NcLinkTimeoutException        1ms   ← 被杀的那台
STRESS_TEST_00001      15      0   -                             1ms
STRESS_TEST_00002      15      0   -                             1ms
STRESS_TEST_00003      15      0   -                             0ms

=== 判定 ===
掉线设备被识别      : 是
其余设备是否受影响  : 未受影响 ✓（无一次失败）
```

要点：

- 被杀的设备从第 11 秒起稳定失败，失败类型是**自己的请求超时**（`NcLinkTimeoutException`），
  不是异常崩溃；
- 其余 3 台在整个 26 秒里**一次失败都没有**，延迟稳定在 0–1ms；
- MQTT 连接**始终没有断开**（日志中无 `Disconnected`）。

**为什么不会串扰**：每个请求都有独立的 GUID 与独立的 `TaskCompletionSource` + 超时。
一台设备不回响应，只会让它自己那个请求超时，不会影响其他设备已注册的等待项。
测试中还特意做了"严格匹配优先、降级匹配兜底"的两段式关联，避免并发请求互相抢响应。

## 三、官方 apiServer：无法判定，因为它本身连不上设备

### 现象

4 台设备全部在线、模拟器进程正常，但 apiServer 对每一台的请求都返回：

```json
{"status":"FAILED","code":12,"value":null}
```

`code = 12` 即 `EXECUTE_ERR_DEVICE`（手册定义："设备 sn 号异常，可能是设备 sn 号错误，
或者设备未连接到 mqtt 服务器"）。

**这是测试开始前的状态**，不是掉线造成的。因此没有可用基线，无法据此判断掉线隔离行为。

### 根因（已定位到这一步）

apiServer 日志：

```
c.n.nclink.apiserver.core.DeviceFactory : 无权连接          ← GBK 显示，原文 "无权连接"
org.eclipse.paho.client.mqttv3.MqttSecurityException: 无权连接
    at ...ExceptionHelper.createMqttException(ExceptionHelper.java:28)
    at ...ClientState.notifyReceivedAck(ClientState.java:1040)   ← CONNACK 处理
    at ...CommsReceiver.run(CommsReceiver.java:151)
```

即 **apiServer 的 MQTT 客户端建立连接时被拒绝**（CONNACK 返回码 4/5 量级），
随后 `deviceFactory No Such Device:STRESS_TEST_00000`。

用 EMQX 的事件主题 `$SYS/brokers/+/clients/+/connected` 监听确认：
**apiServer 的 MQTT 客户端从未出现在 Broker 的客户端列表里**——连接根本没建成。

### 已排除的原因（都做了实测）

| 假设 | 实测结果 | 结论 |
|---|---|---|
| EMQX 授权拦截 | 规则为 `no_match=allow` + 末条 `{allow, all}`；`deny_action=ignore` | 排除 |
| clientId 格式/长度 | EMQX 接受普通、空、含斜杠、含空格、中文、200 字符等 id | 排除 |
| MQTT 协议版本 | 3.1 / 3.1.1 / 5.0 均可连接 | 排除 |
| 空用户名/空密码 | EMQX 未开认证，空凭据、错误凭据都能连 | 排除 |
| Paho 1.2.2 与 EMQX 5.3 不兼容 | **用 apiServer 自带的 Paho 1.2.2 直接连同一台 EMQX，全部成功**（见 `<复现工程目录>\`） | 排除 |
| JDK 版本问题 | JDK 8 与 JDK 17 下现象完全相同 | 排除 |
| 外部配置未生效 | 把 `mqtt.url` 指向不存在的端口后，apiServer 确实按新配置连（端口变了） | 配置能生效 |

### 结论

不是 Broker、不是 Paho 版本、不是凭据、不是 JDK。**问题在 apiServer 自身的调用方式或其内部配置**，
且用同一份 Paho + 同一个 Broker 的独立程序无法复现。apiServer 是闭源 jar，我无法进一步定位。

## 四、给现场的建议

1. **apiServer 这条链路要先修通再谈掉线行为。** 建议向华中数控索取：
   - 与该版本 apiServer 配套的**目标环境**（手册写的是 EMQX **4.2.7**，而当前用的是 **5.3.0**）；
   - 该版本 apiServer 的 MQTT 连接方式说明（是否要求特定 clientId 规则或特定 Broker 配置）。
   已知线索：仓库里那份 EMQX 配置目录的历史日志（2023-11-30）显示，当时有人从
   `192.168.0.109:18083` 用 Postman 请求过 `/v1/STRESS_TEST_00001/data`，
   说明**这套材料曾经跑通过**，环境差异值得追。

2. **如果要立刻上线，用我们自己的 C# 客户端（方案 B）。** 它不依赖 apiServer，
   4 台设备掉线隔离已实测通过。需要注意本节下一条。

3. **采样数据的设备归因**：`Sample/{channelId}` 主题里**不带设备 SN**。
   若多台设备使用相同的采样通道 id（如都用默认的 `sample_channel0`），
   上位机无法判断数据属于哪台设备。本库遇到这种歧义会**丢弃该帧**而不是错误归因。
   生产环境请做到其一：
   - 每台设备的采样通道 id 唯一；或
   - 每台设备用独立的 `NcLinkClient` 连接。

## 五、复现用环境说明

- MQTT Broker：EMQX 5.3.0，`<EMQX_HOME>`（原目录含中文，官方要求英文路径）
- JDK：`<JDK8_HOME>`（1.8.0_341，32 位）、`<JDK17_HOME>`（17.0.12）
- apiServer 配置：`../厂家资料/application.yml`（指向本地 EMQX）
- Paho 复现工程：`<复现工程目录>\`（含 `PahoProbe.java` / `PahoProbe2.java`）
  编译运行：
  ```powershell
  cd <复现工程目录>
  <JDK8_HOME>\bin\javac.exe -cp "lib\org.eclipse.paho.client.mqttv3-1.2.2.jar" PahoProbe2.java
  <JDK8_HOME>\bin\java.exe -cp "lib\org.eclipse.paho.client.mqttv3-1.2.2.jar;." PahoProbe2 tcp://127.0.0.1:1883 probe2-aaa
  ```
