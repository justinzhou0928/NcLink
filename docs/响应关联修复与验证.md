## 一、修的问题：响应关联误领（迟到响应被当成本次结果）

### 现象

隔离测试中出现自相矛盾的结果：某台模拟机床的进程**已被确认杀死**（结束核对
`存活=False`），但几秒后的探测却返回了 `OK`。

```
  [14:52:16] === 杀掉 STRESS_TEST_00002 ===
  已终止 STRESS_TEST_00002 的模拟器进程 pid=17288
  ...
  [14:52:27] 00000=FAIL(2514ms)  00001=OK(1ms)  00002=OK(0ms)  00003=OK(1ms)
                                     ↑ 该进程已死，不可能响应
```

### 根因

`NcLinkClient.ProbeAsync` 的兜底匹配条件过宽：

```csharp
// 修复前
matcher: text => text.Contains("\"model\"", StringComparison.Ordinal)
                 || text.Contains(deviceId, StringComparison.Ordinal)
                 //  ↑ deviceId 也出现在响应主题 Probe/Query/Response/{SN} 里
```

而匹配是「严格条件不满足就退到宽松条件」，于是某台设备的**迟到响应**
（超出本请求超时后才到达）会满足**下一个**请求的宽松条件，被下一个请求认领——
表现为"设备已死却返回 OK"。

危害不是崩溃，而是**把过期数据当作本次结果**，生产上会导致误判且极难发现。

### 修复内容（`src/NcLink.Core/Client/NcLinkClient.cs`，4 处）

1. `PendingRequest.StrictMatcher` / `FallbackMatcher` 类型由 `Func<string, bool>`
   改为 `Func<string, string, bool>`（多传「收到报文的主题」）。

2. 降级匹配**新增** `TopicMatches(到达主题, 请求主题)` 前置校验：
   响应主题前缀必须与请求类型对应（Query→Query/Response 等），
   且主题尾部的设备 SN 必须与请求一致。

3. `ProbeAsync` 的 matcher 改为只用「主题是 Probe 响应」+「报文含 model」判定，
   **彻底不再用 deviceId 兜底**。

4. 新增私有方法 `TopicMatches`。

### 修复后的性质

- 设备的迟到响应**不可能**再被后续请求认领；
- 代价：若设备**不回显 `@id`**，非 Probe 请求在降级匹配时仍要求
  「响应主题匹配 + 数据项 id 有交集」，稍严于修复前。
  真机是否回显 `@id` 需现场确认（模拟器会回显）。

## 一、要修的问题：响应关联误领（stale response 被当成本次结果）

### 现象

隔离测试中观察到自相矛盾的结果：某台模拟机床的进程**已被确认杀死**（结束核对
`存活=False`），但几秒后的探测却返回了 `OK`。

```
  [14:52:16] === 杀掉 STRESS_TEST_00002 ===
  已终止 STRESS_TEST_00002 的模拟器进程 pid=17288
  ...
  [14:52:27] 00000=FAIL(2514ms)  00001=OK(1ms)  00002=OK(0ms)  00003=OK(1ms)
                                     ↑ 该进程已死，不可能响应
```

### 根因

`NcLinkClient.ProbeAsync` 的兜底匹配条件过宽：

```csharp
// 修复前
matcher: text => text.Contains("\"model\"", StringComparison.Ordinal)
                 || text.Contains(deviceId, StringComparison.Ordinal)
                 //  ↑ deviceId 也出现在响应主题 Probe/Query/Response/{SN} 里
```

而匹配逻辑（`OnMessageAsync`）是：

```csharp
if (text.Contains(messageId)) return true;   // 严格：@id 命中
if (matcher(topicOfMsg, text)) return true;  // 宽松：含 "model" 或含 deviceId
```

于是当某台设备的响应**迟到**（超过本请求超时后才到达），它会满足**下一个**请求的
宽松条件（因为报文体里有 `"model"`、主题里有该 SN），被下一个请求认领 ——
表现为"设备已死却返回 OK"。

这类问题的危害不是崩溃，而是**把过期数据当作本次结果**，在生产上会造成误判且很难发现。

### 修复内容（`src/NcLink.Core/Client/NcLinkClient.cs`，3 处）

1. `PendingRequest.StrictMatcher` 与 `FallbackMatcher` 的类型由
   `Func<string, bool>` 改为 `Func<string, string, bool>`（多传一个「收到报文的主题」）。

2. `SendAsync` 内的匹配逻辑：
   - 严格匹配：`text.Contains(messageId)` 或自定义 matcher（现在可拿到主题）；
   - 降级匹配：**新增** `TopicMatches(到达主题, 请求主题)` 前置校验，
     要求响应主题前缀正确、且设备 SN 与请求一致。

3. `ProbeAsync` 的 matcher 改为：

```csharp
// 修复后：只用「主题是 Probe 响应」+「报文含 model」判定，彻底不用 deviceId 兜底
matcher: (topicOfMsg, text) =>
    topicOfMsg.StartsWith(NcLinkTopics.ProbeQueryResponsePrefix, StringComparison.Ordinal)
    && text.Contains("\"model\"", StringComparison.Ordinal),
```

4. 新增私有方法 `TopicMatches`：把 `Query/Set/ProbeQuery/ProbeSet` 的请求前缀映射到
   对应响应前缀，再比对主题尾部的设备 SN。

### 修复后应具备的性质

- 设备的迟到响应**不再可能**被后续请求认领（Probe 已无 deviceId 兜底；
  Query/Set 的兜底必须同时满足"响应主题匹配 + 数据项 id 有交集"）；
- 代价：若设备**不回显 `@id`** 且不是 Probe 响应，Probe 会超时失败
  （这是有意的取舍——宁可超时，也不要领错数据）。真机是否回显 `@id` 需现场确认；
  若不回显，应改为「按主题精确匹配 + 一次只允许一个在途 Probe」的策略。
